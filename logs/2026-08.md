# 2026-08 作業ログ

## 2026-08-26 精度改善パス1（モデル据え置き）

### 現状把握
- 精度を決めているのは `transcriptions.create(model="whisper-1", file=...)` の1行。言語指定もプロンプトも無し
- 25MB超は10分固定でぶつ切り（文の途中で必ず切れる）。しかも時間ベースなので WAV 等では10分で25MBを超え、分割しても弾かれる
- `temp_{filename}` / `temp_chunk_{i}` が固定名で同時リクエストで衝突
- フロントは `audio/*` 限定で動画ファイルを弾く

### 実施内容（PR: feat/accuracy-pass1）
- `language="ja"` を明示（冒頭の言語誤判定・英訳返し対策）
- 送信前に ffmpeg で 16kHz mono mp3 64kbps に再エンコード（Whisper 内部と同じ条件なので損失なし）。25MB で約54分入るので大半は分割不要に。動画からは音声トラックだけ抜く
- それでも超える場合は `silencedetect` の無音中点で貪欲分割。各区間が上限以下であることを保証
- `prompt` に「見本文 + ユーザー用語ヒント + 前チャンク末尾60文字」を渡す。Whisper は長いと先頭から捨てるので重要なものを後ろに置く
- UI に「用語ヒント」textarea 追加（localStorage に保存）。SW キャッシュ v3
- 一時ファイルは `tempfile.mkdtemp` でリクエスト毎に隔離
- 設定は環境変数で上書き可（`TRANSCRIBE_MODEL` / `TRANSCRIBE_LANGUAGE` / `TRANSCRIBE_PROMPT` / `TRANSCRIBE_PREV_TAIL_CHARS`）

### 検証（Gドライブの実録音 m4a を使用）
- 46分 33.8MB → 再エンコード後 22.2MB、分割なし（旧コードだと5チャンク）
- 56分 40.7MB → 26.7MB、無音位置 2821s で2分割
- 4分抜粋で上限を1MBに落として分割経路を実走: 117s の無音で切れ、前チャンク末尾が次のプロンプトに繋がるのを確認
- HTTP 経由で用語ヒント付き60秒: 正常応答、句読点あり

### レビュー対応（@claude、PR #1）
- 分割後の実サイズを `ensure_fits` で検証、超過なら無音位置で二分して再帰（平均ビットレート見積もりが外れても送信前に収める）。API上限を400KBに落として8分割になるのを確認
- `probe_duration` / `detect_silence_midpoints` の returncode 未チェックを `_check` で統一。duration<=0 も弾く
- `_run` に timeout（既定600秒）、ffmpeg 不在は起動時に警告＋実行時に明示エラー
- エンドポイントを `async def` → `def` に。FastAPI がスレッドプールで回すのでイベントループを塞がない
- ヒント欄 maxlength=200、サーバ側でも200文字で切る

### 残課題（次のパス）
- 「粘度→粘土」「業界標準→了解標準」のような同音異義の誤変換が残る。用語ヒントで一部は消えるが、根治は LLM 後処理
- モデル A/B（whisper-1 vs gpt-4o-transcribe vs gpt-transcribe）。gpt-transcribe は `keywords` / `languages` を持つが `language` 単数は非対応なので切替時に分岐が要る
- 話者分離は `gpt-4o-transcribe-diarize` で Render free のまま可能（prompt 非対応）

## 2026-08-26 パス2: モデル A/B → gpt-transcribe を既定に

### A/B（`scripts/ab_compare.py`、実録音4分抜粋、用語ヒントあり）
| model | 文字数 | 欠落 | 用語 |
|---|---|---|---|
| whisper-1 | 860 | 中盤の一段落を飛ばす | 革新/粘土/了解標準（誤） |
| gpt-4o-transcribe | 757 | **冒頭40秒を丸ごと落とす** | 確信/粘土（誤）、業界標準/イータ（正） |
| gpt-transcribe | 988 | なし | 核心/粘度/η/業界標準 すべて正 |

- gpt-transcribe は `keywords` が効く。ヒントに「菊池」を入れたら人名も直った
- prompt の効き方がモデルで違う: whisper-1 は「見本文」、gpt-transcribe は「文脈＋指示文」。指示文で「あの」「えっと」「で、」が消える。見本文だと同じ箇所で「革新」に化けた（非決定的だが傾向は明確）
- gpt-transcribe は `language` 単数非対応 → `languages=[..]`、`keywords` を `extra_body` で渡す（SDK 2.8.1 は未対応だが multipart でも extra_body は届く）
- 速度も whisper-1 の半分（12s→6.6s）、単価も安い（$0.006→$0.0045/分）
- 注意: この A/B は当時の既定（whisper-1）の見本文プロンプトを3モデル共通で使っていた（Codex 指摘で判明、既定プロンプトが import 時に固定されていた）。gpt-transcribe は不利な条件でも勝っており、指示文プロンプトに変えると更に改善（別途60秒で確認）。次回 A/B からはモデル別プロンプトが正しく効く

### 実装
- 既定 `TRANSCRIBE_MODEL=gpt-transcribe`。モデル別の既定プロンプト（`DEFAULT_PROMPTS` / `GPT_DEFAULT_PROMPT`）、`TRANSCRIBE_PROMPT` で上書き可
- `transcribe_file` にモデル差分を閉じ込め、用語ヒントを `split_keywords` で keywords 化
- 分割経路（強制2分割）を gpt-transcribe で実走、境界の文脈継続OK
